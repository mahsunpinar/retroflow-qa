# StackCraft Engineering — QA & Test Standards
**Version 2.0 · Effective from Q1 2025 · Applies to all backend projects**

---

## 1. Coverage Requirements

### 1.1 Business rule coverage (CRITICAL)
Every business rule stated in a project's brief or spec must have at least one executable
test that verifies it against a running instance of the application — not a unit test on an
isolated method in a vacuum. Unit-level coverage is welcome in addition, not instead.

Violation severity: **Critical**

### 1.2 Minimum coverage thresholds
Line coverage must be at least 80%. Branch coverage must be at least 70%. These are floor
values, not targets — 100% line coverage with weak assertions is worse than 80% coverage
with meaningful ones.

Violation severity: **Major**

---

## 2. Assertion Quality

### 2.1 No tautological assertions (CRITICAL)
An assertion that would pass regardless of what the system under test actually returned is
prohibited. `assertThat(result).isNotNull()` on a call that always returns a non-null object
is not a meaningful test.

```java
// PROHIBITED
assertThat(response.getBody()).isNotNull();

// REQUIRED
assertThat(response.getBody().getStatus()).isEqualTo("CLOSED");
```

Violation severity: **Critical**

### 2.2 Every test must assert on behaviour, not just status code
A test that only checks an HTTP status code, when the endpoint's purpose is to return or
change specific data, is incomplete. Status code checks are necessary, not sufficient.

Violation severity: **Major**

### 2.3 Negative and boundary cases are mandatory
For every business rule with a "must not" or "cannot" clause, there must be a test that
attempts the prohibited action and verifies it is rejected — not just a test of the allowed
path.

Violation severity: **Major**

---

## 3. Test Independence & Reliability

### 3.1 No order dependency
Tests must produce the same result regardless of execution order. A test suite that only
passes in one specific order is not trustworthy and must be fixed before merge.

Violation severity: **Critical**

### 3.2 No shared mutable state between tests
Each test must set up its own required state. Tests must not rely on data created by a
previous test in the same run.

Violation severity: **Major**

### 3.3 Flaky tests are not "usually passing" tests
A test that fails intermittently is broken, not "occasionally slow." A flaky test must be
fixed or explicitly quarantined with a tracked ticket — it must never be silently retried
until green and merged.

Violation severity: **Critical**

---

## 4. Bug Reporting

### 4.1 Required bug report format
Every bug logged must include:
- **Severity**: Critical / High / Medium / Low
- **Reproduction steps**: the exact request(s) sent
- **Actual result**: the exact response received (status code and body)
- **Expected result**: what the spec or brief says should have happened
- **Business impact**: what happens if this ships as-is

A bug report without reproduction steps and actual evidence is not a bug report — it's a
guess, and will be closed as "cannot reproduce."

Violation severity: **Critical** (for reports missing reproduction evidence)

### 4.2 Severity definitions
| Severity | Definition |
|---|---|
| Critical | Data loss, a business rule silently bypassed, or a security/compliance exposure |
| High | A core flow is broken or produces incorrect results with no workaround |
| Medium | A flow is broken but has a workaround, or an edge case behaves incorrectly |
| Low | Cosmetic, or affects a rarely-used path with minimal business impact |

## 5. AI-Assisted Test Generation

### 5.1 Every AI-generated test must be run before being trusted
A generated test that has never actually been executed against the running application must
not be included in a coverage claim or a release report. "The AI wrote a test for this" is
not equivalent to "this is tested."

Violation severity: **Critical**

### 5.2 AI-reported "coverage" claims must be independently verified
If an AI tool states that a business rule is covered by a specific test, the test must be
opened and read to confirm it actually verifies that rule, before the claim is repeated in
any report.

Violation severity: **Critical**

### 5.3 Test smell review is mandatory for AI-generated suites
Any test suite substantially generated by AI must go through an explicit test-quality review
pass (tautological assertions, shallow coverage, order dependency) before being merged.
Generation speed does not exempt a suite from this review.

Violation severity: **Major**

---

## 6. Reporting to Stakeholders

### 6.1 Explicit scope disclosure
Any quality or release report must explicitly state what was NOT tested or verified, not
just what was. Silence on a topic must never be interpreted as "it was fine."

Violation severity: **Critical**

### 6.2 No internal jargon in release recommendations
A release recommendation (BLOCKED / CONDITIONAL / APPROVED, or equivalent) must be
accompanied by a plain-language explanation a non-technical stakeholder could act on.

Violation severity: **Minor**
